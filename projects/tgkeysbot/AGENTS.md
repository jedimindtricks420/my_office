# AGENTS.md — tgkeysbot

Инструкции для ИИ-агентов, работающих над документацией/задачами проекта
`tgkeysbot` в `my_office`. Общие правила — в корневом
[`/AGENTS.md`](../../AGENTS.md); этот файл их не дублирует, только специфику
проекта.

## Проект

- **Исходный код (source of truth для кода):** `/home/admin1/tgkeysbot/` —
  отдельный каталог вне `my_office`. Этот репозиторий
  (`my_office/projects/tgkeysbot/`) содержит только документацию и задачи,
  НЕ код.
- **Не изменяй `/home/admin1/tgkeysbot/` из задач `my_office`**, если задача
  явно не требует правок кода и это не согласовано отдельно.
- **У проекта нет собственного git-репозитория** (`/home/admin1/tgkeysbot/`
  не является git-репозиторием — подтверждено `git status`). История
  изменений кода недоступна, только mtime файлов на диске.
- Приложение — Django-проект (`core` app, back-office/каталог) + отдельный
  долгоживущий процесс Telegram-бота (aiogram + Pyrogram), оба используют
  одну и ту же PostgreSQL БД через Django ORM. Три сервиса в
  `docker-compose.yml`: `db`, `web`, `bot`.
- Внешний сервис, к API которого обращается `bot/drweb_client.py`
  (Dr.Web-ключи), задокументирован отдельно — см.
  [`../drweb-key-service/`](../drweb-key-service/AGENTS.md) (исходный код:
  `/home/admin1/drweb-key-service/`, отдельный проект). Связь подтверждена
  только со стороны кода `tgkeysbot` (`DRWEB_API_URL`/`DRWEB_API_TOKEN`),
  не перепроверялась со стороны самого сервиса.
- Django-админка этого проекта развёрнута на общем с проектом
  `keyspro_auto_sender` домене `webhook.keyspro.uz`, по пути `/partner_bot/`
  (см. [DEPLOYMENT.md](docs/DEPLOYMENT.md)). Это отвечает на открытый вопрос
  №8/№15 из `my_office/projects/keyspro_auto_sender/docs/OPEN_QUESTIONS.md`
  ("что за backend на 127.0.0.1:8080") — обновление того файла в рамках
  этой задачи не делалось (вне области, см. корневой `AGENTS.md` п.7).

## Известные особенности проекта (важно для агентов)

- **Два независимых источника выдачи ключа** для товара
  (`Product.delivery_source`): `telegram_bot` (Pyrogram-аккаунт от лица
  пользователя шлёт команду боту `@MicrosoftLeo_Bot` и парсит ответ
  регэкспом по истории чата, ждёт 60 секунд) и `drweb` (HTTP-запрос к
  внешнему сервису `drweb-key-service`).
- **Списание баланса происходит после выдачи ключа, а не до неё**, и нет
  проверки `negative_limit` перед началом покупки — партнёр может уйти в
  долг без ограничения количества последующих покупок. `debt_limit_notified`
  лишь один раз показывает предупреждение при пересечении лимита. См.
  [OPEN_QUESTIONS.md](docs/OPEN_QUESTIONS.md).
- **`transport/tasks.py` — нерабочий/неподключённый код.** Реализует
  Celery-задачи с Redis-блокировкой (`lock:source_account:default`) для
  того же сценария (покупка/активация), но пакеты `celery` и `redis`
  отсутствуют в `requirements.txt`, нет ни одного `Celery(...)` приложения
  в коде и нет сервиса worker/Redis в `docker-compose.yml`. Реально
  работает только инлайн-логика в `bot/main.py` (без блокировки —
  единственный Pyrogram-клиент, конкурентные заказы не сериализуются).
- **`session_generator.session` (живая Pyrogram-сессия), `keyspro.db` и
  `media.tar.gz` не исключены `.dockerignore`** и подтверждённо copy'ятся
  внутрь Docker-образа (`docker exec ... ls /app/`). `session_generator
  .session` функционально эквивалентен активному токену входа в Telegram-
  аккаунт, использованный для Pyrogram. Не исправлялось в рамках этой
  задачи (только документирование). См. [OPEN_QUESTIONS.md](docs/OPEN_QUESTIONS.md).
- **`.env.example` содержит значения, похожие на настоящие**, а не
  плейсхолдеры, для `CLIENT_BOT_TOKEN`, `ADMIN_TELEGRAM_ID`, `API_ID`,
  `API_HASH` (в отличие от `SESSION_STRING`/`SECRET_KEY`/
  `POSTGRES_PASSWORD`, которые явно помечены как `your_..._here`/
  `change_me`). Значения НЕ скопированы в документацию `my_office` ни в
  каком виде. См. [OPEN_QUESTIONS.md](docs/OPEN_QUESTIONS.md).
- **`keyspro.db` в корне проекта — не используемый Django-кодом файл** с
  другой схемой (таблицы `partners`/`products`/... во множественном числе,
  без `django_`-таблиц) — вероятно, остаток более ранней (до-Django)
  версии проекта. Продакшн использует PostgreSQL через `DATABASE_URL`
  (подтверждено `docker exec`), `db.sqlite3` — Django-схема, но тоже не
  используется в контейнерах (только при локальном запуске без
  `DATABASE_URL`).
- Секреты (`.env`, `session_generator.session`, содержимое БД — может
  включать реальные Telegram ID партнёров, их баланс и выданные
  лицензионные ключи) не читались построчно и не должны копироваться в
  документацию `my_office`. Фиксируются только имена переменных и схема, не
  значения/данные.
