# ADR-0010: Подтверждение счёта и контрольных итогов банковской выписки

Дата: 2026-09-10. Статус: реализовано локально, не выпущено.
TASK-0005, частичная защита ACC-048/054.

## Причина

Импорт не сравнивал счёт выписки с выбранным BankAccount. Парсер 1С считал
неопознанное направление расходом, нормализовал невозможные даты и использовал
parseFloat. Ошибка конечного остатка была предупреждением после записи.

## Решение

- Номер счёта: строка из 20 цифр, разрешены пробельные разделители без потери
  ведущих нулей. Номер выписки обязателен и сравнивается с собственным BankAccount
  до preview и повторно под блокировкой счёта перед записью. Несовпадение или
  отсутствие номера: 422 BANK_STATEMENT_INVALID, без изменений учёта.
- В 1С допустим единственный собственный счёт и одна секция его итогов.
  Ровно одна сторона операции должна совпадать с ним; обе стороны содержат
  распознанные номера. Незавершённые секции и повторные поля отклоняются.
- Даты проверяются календарно в формате DD.MM.YYYY; период и оба остатка
  обязательны. Все операции должны входить в этот период.
- Суммы 1С сохраняются как строки с двумя знаками. Положительные операции и
  знаковые остатки проверяются целиком, без parseFloat; экспонента, мусор,
  избыточная точность и переполнение Decimal(20,2) отклоняются. Контроль
  opening + credits - debits = closing считается BigInt в сотых до транзакции.
- При добавлении строк конечный остаток счёта должен точно совпасть с выпиской;
  иначе все записи, включая аудит и созданные периоды, откатываются. Полностью
  повторная выписка не меняет банк и не сверяет текущий остаток с историческим.
- UTF-8 декодируется строго, иначе используется CP1251. Старый числовой формат
  суммы сохранён только при вычислении legacy-хеша; найденная строка проверяется
  точным сравнением суммы и исходных полей. Bank-v2 хеш остаётся с fixed-2 суммой.
- Multipart проверяет типы/повтор полей, непустой файл до 5 МиБ. Превышение: 413;
  неверная форма: 400. Проверка file.size выполняется после req.formData(),
  поэтому это не транспортный лимит памяти для всего HTTP-тела.
- Неподтверждённый Excel/неизвестный формат получает 422
  BANK_STATEMENT_UNSUPPORTED до вызова Excel-парсера. Это временное отключение,
  не реализация схем банков или карантина. Step1 предлагает только TXT.
  Preview API возвращает точные строковые суммы; Step1 не вызывает preview.

## Проверка

48 тестов реального парсера и 64 SQL-теста банковского API/отката прошли.
Проверены UTF-8/CP1251, неверные счета/даты/суммы, контрольная разница в копейку,
отрицательные остатки, multipart/размер/отказ Excel, смена номера перед lock.
Реальный файл проходит API и PostgreSQL: 9007199254740993.27 сохраняется и
откатывается точно, legacy 0.1 не дублируется при новом строковом 0.10.
Общая регрессия 22:00:43: 979 тестов/46 файлов, 158 PostgreSQL, 28,76 с.
Финальные TSC, scoped lint и диагностика редактора прошли; два прежних
предупреждения конфигурации lint.
Браузер, production, сборки, миграции и перезапуски не использовались.

## Ограничения

Валюта выписки не подтверждается; обязательность/уникальность номера в БД
не введена. Это локальная проверка 20-значного формата, не поддержка IBAN.
Последовательность периодов, банковский reference, оригинал/хеш файла,
версия формата и полный регистр партий отсутствуют. Совпадение итогов не
доказывает полноту истории; CLOSED/locked строки пока пропускаются.
Полная грамматика файла и все банковские варианты 1С не проверены на реальных
образцах. Excel-парсер всё ещё содержит прежнюю эвристику, но недоступен через
этот импорт. Общий тип ParsedTransaction допускает number для старого парсера;
точный строковый контракт обеспечен только для нового пути 1С.
Ограничения отката по AuditLog сохраняются: [ADR-0009](ADR-0009-bank-import-rollback.md).
ACC-048/054, все 57 замечаний и G0-G4 не завершены.
