# ADR-0015: защищённая первичная инициализация остатков

Дата: 2026-09-11. Статус на 2026-09-12: реализовано; частичный выпуск
11 сентября не является приёмкой аналитических остатков/корректировок.
Выпуск и границы provenance: [DEPLOYMENT](../DEPLOYMENT.md).
Журнал проверок ниже относится к разработке до выпуска.

**Сверка `4254a27` 2026-09-12:** одноразовый endpoint присутствует, но
OPENING_BALANCE не включён в documentPolicy и защиту движка. Описанный ниже
запрет общих post/void/repost не подтверждается этим снимком.
Блокер: [STATUS](../STATUS.md).
Задача: [TASK-0005](../../tasks/active/TASK-0005-accounting-correctness-remediation.md).

## Решение

Прежняя замена начального баланса удаляла историю, использовала number и
выбирала первый OPEN-период независимо от даты. До реализации версионных
корректировок разрешена только первичная инициализация организации без документов.

- Общая схема `openingBalanceInput.ts` для API/UI: строгая дата 1900–9999,
  2–500 строк, уникальные четырёхзначные счета, одна положительная сторона
  строки, до 18 целых и 2 дробных цифр. API нормализует допустимые совместимые
  number, UI отправляет строки; точные итоги считаются Decimal с precision 40.
- Разрешены только действующие листовые балансовые счета до 9000, не группы
  `xx00`, не TRANSIT/OFF_BALANCE. Дебет должен точно равняться кредиту;
  автоматической балансировки через 8890 нет.
- POST требует актуальное членство и OWNER/ADMIN/ACCOUNTANT. Дата переводится
  в полночь Asia/Tashkent и выбирает соответствующий существующий месяц.
  Период автоматически не создаётся; CLOSED/lockDate/closingData и любые
  существующие документы, включая VOIDED, запрещают новую инициализацию.
- Транзакция блокирует Organization FOR UPDATE и собственные периоды по
  year/month FOR NO KEY UPDATE; документ, движения и CREATE_OPENING_BALANCE
  записываются атомарно. Payload содержит version=1, дату, строки и итоги;
  это версия формата снимка, НЕ модель неизменяемых версий документа.
- Общие API и сам posting engine запрещают post/void/repost OPENING_BALANCE;
  превращение обычного документа в OPENING_BALANCE отклоняется до изменений.
- GET возвращает исходную дату и все денежные строки, включая legacy 8890,
  только для чтения. Несколько POSTED начальных балансов дают 409
  OPENING_BALANCE_REQUIRES_REVIEW. UI не выдаёт ошибку загрузки за пустой баланс,
  поддерживает retry, отмену и сроки ожидания загрузки/записи 15/20 секунд.

## Ограничения

ACC-016 остаётся частично реализованным. Нет аналитических начальных регистров
контрагентов/договоров, запасов и ОС, контролируемой корректировки и DB-инварианта
единственной активной версии. Прямой SQL не защищён этим маршрутом. Запрет
перезаписи не заменяет требуемый бухгалтерский lifecycle. Полная гонка ввода
остатков с закрытием/другими FK-писателями отдельно не доказана.

## Проверка

45 mock/API/schema, 3 DOM и 8 PostgreSQL-тестов первичного баланса; дополнительные
отказы общих API и движка включены в document-api/posting-transaction.
SQL подтверждает сумму 9007199254740993.27, Ташкентскую дату, единственный
успех двух параллельных инициализаций, откат при ошибке аудита, отказ неверному
периоду и сохранность движений при попытке замены. DOM проверяет точные строки,
восстановление read-only и retry; браузер не запускался.
