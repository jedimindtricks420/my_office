# ADR-0016: архив снимков проведения

Дата: 2026-09-11. Статус: реализовано и проверено локально, не выпущено.
Задача: [TASK-0005](../../tasks/active/TASK-0005-accounting-correctness-remediation.md).

## Контекст и решение

Обычный void удаляет JournalEntry, repost меняет тот же Document, а
ensureBaseData обновляет текущие шаблоны. Транзакции предотвращают частичный
результат, но не сохраняют прежние значения. Как ограниченный первый этап
ACC-001/037/040/043/051/053 добавлен PostingRevision, независимый от рабочей
проекции журнала. Это не завершение версионной модели или реализация сторно.

`postDocument` после записи движений и OpenItem добавляет POST-снимок до
аудита/календаря. `voidDocument` после проверок, но до удаления движений и
изменения связей добавляет VOID-снимок. Repost активного документа сохраняет
VOID и POST в той же транзакции. Повторный void уже VOIDED не создаёт запись.
Сбой архива, календаря или следующего шага откатывает транзакцию целиком;
вызывающий код обязан пробрасывать ошибку, как и в ADR-0002.

Снимок formatVersion=1 содержит:

- исходный Document с payload, датой и идентификаторами;
- observedType с полным прочитанным postingTemplate;
- фактические JournalEntry с кодами счетов и связанными OpenItem;
- для POST: engineVersion=posting-v1, фактический isVatPayer, vatRate и settings;
- ruleProvenance: USED_FOR_POSTING для POST, OBSERVED_AT_VOID для VOID.

Денежные поля из SQL numeric преобразуются непосредственно в текст, без
Number. JSONB хранится вместе с SHA-256 его канонического PostgreSQL-текста.
Хеш проверяется CHECK; это контроль содержимого, не подпись автора и не
криптографическая цепочка заголовков. createdAt показывает время начала
транзакции; порядок задаёт revision, а не время.

Документ уже заблокирован движком. INSERT-триггер дополнительно блокирует
живой Document и сверяет orgId/periodId, последовательный номер, previousId
и неизменность tenant цепочки. Уникальны documentId/revision и previousId.
UPDATE/DELETE/TRUNCATE архива запрещены SQL-триггерами.

Намеренно нет FK из архива к живым Document/Organization/Period/Account:
снимки должны сохраняться при удалении исходных записей. При вставке требуется
существующий документ своей организации и периода; после удаления источника
новые ревизии не добавляются. Идентичность хранится в снимке и заголовке.
Это не новая политика разрешения удаления организаций или учётных документов.

## Чтение и экспорт

Продолжение 2026-09-11 добавляет два read-only API, без новой миграции:

- `GET /v2/api/posting/revisions?documentId=...&cursor=...`: до 20 метаданных,
  убывающий revision, nextCursor либо null. Снимки не загружаются. Курсор
  ограничен одновременно orgId и documentId; новый POST не сдвигает старую
  страницу. Время транзакции не используется для сортировки.
- `GET /v2/api/posting/revisions/[revisionId]/export`: JSON с
  exportVersion=posting-revision-v1 и revision, включая заголовок,
  snapshotHash и snapshotCanonical. Последнее поле является строкой точного
  PostgreSQL `snapshot::text`, а не повторно сериализованным объектом.
  SHA-256 проверяется сервером и может быть независимо рассчитан по UTF-8
  байтам этой строки. Это сохраняет исходное представление JSON numeric;
  потребителю нужен decimal-aware parser для больших JSON-чисел.

Каждый запрос заново проверяет членство через getActiveMembership, все
чтения фильтруются по orgId. Поддерживаются фактические OWNER/ADMIN/ACCOUNTANT;
VIEWER в текущем enum OrgRole отсутствует. Живой Document для чтения не нужен:
история доступна после удаления документа, пока существует членство в организации.
После удаления организации сохранённые снимки не открываются по старой cookie.
Чужой/отсутствующий documentId возвращает одинаковый пустой список; чужая/
отсутствующая ревизия или курсор дают 404. Ошибки входа 400, сессии 401,
членства 403, целостности экспорта 409; внутренние ошибки скрываются за 500.
Все ответы private/no-store и nosniff, имя загрузки фиксировано.

## Границы

- Рабочие Document/JournalEntry/OpenItem остаются изменяемыми; void удаляет
  активные движения, а отчёты продолжают читать рабочую проекцию, не архив.
- Покрыты только вызовы этих сервисов. Прямые записи, отдельная инициализация
  остатков, все версии закрытия и весь lifecycle первички не охвачены.
- Снимок фиксируется в точке вызова сервиса, не после всех возможных изменений
  внешнего сценария. Это не атомарный архив всех производных регистров.
- Для старых документов первый VOID сохраняет имеющиеся движения, но текущий
  шаблон честно помечается OBSERVED_AT_VOID: историческое правило неизвестно.
  Backfill и восстановление ранее удалённых проводок не выполняются.
- engineVersion не заменяет сохранение исходного кода вычислителя, effective-date
  правила, версии налоговых маппингов и воспроизводимый replay.
- Нет UI архива, поиска документов по всему архиву, RLS, утверждённых SQL-ролей,
  политики retention, лимитов роста архива/размера одного экспорта или
  проверенного backup/restore. Список требует известный documentId; экспорт
  загружает один снимок целиком. Хеш проверяется при экспорте, не в списке.
- Владелец БД/superuser может отключить триггеры или удалить таблицу. Это не
  WORM-хранилище и не защита от привилегированного администратора.

таймаут не увеличивать без согласования. Старый образ не пишет архив и создаст
пробелы: откат кода требует остановки записей и сверки. Архив при откате не удалять.
