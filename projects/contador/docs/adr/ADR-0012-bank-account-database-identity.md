# ADR-0012: Проверяемое ограничение банковских номеров в БД

Дата: 2026-09-10. Статус: подготовлено и проверено на синтетических таблицах,
не применено к основной таблице тестовой БД или production. Частичный ACC-048.

## Причина

API-сериализация из [ADR-0011](ADR-0011-bank-account-identity.md) не защищает от
других писателей. Нужны обязательный номер и уникальность внутри организации,
но старые пустые/неверные номера и дубли нельзя исправлять автоматически.

## Решение

Подготовлен raw SQL `v2/prisma/migrations/20260910_bank_account_identity.sql`:

- Одна транзакция; lock_timeout 1 с, statement_timeout 5 с. ACCESS EXCLUSIVE
  захватывается до preflight и удерживается до commit. Чтение таблицы на это
  время также блокируется; требуется отдельное окно и оценка на копии данных.
- Preflight всей таблицы, не одной организации, проверяет нормализованные
  номера и группы дублей. При проблеме выдаются только агрегаты и исключение.
  Ни DDL, ни данные не фиксируются частично.
- NOT NULL, CHECK на 20 ASCII-цифр и уникальный expression index по orgId и
  нормализованному номеру. SQL translate удаляет ровно пробельные символы
  ECMAScript, используемые API; COLLATE C исключает зависимость от сортировки.
- Исходное оформление, ведущие нули, остаток и история не переписываются.
  Равные номера в разных организациях допустимы, валюта не входит в ключ.
- Повторное применение проверяет данные снова и пересоздаёт именованные
  CHECK/index под той же блокировкой, не доверяя только их существованию.
- Конфликт уникальности Prisma P2002 для BankAccount в POST/PUT возвращает
  409 BANK_ACCOUNT_DUPLICATE без записи аудита. API-проверка/advisory lock
  сохраняются для понятной ошибки и совместимости до миграции.

Prisma-поле пока остаётся nullable для совместимости с немигрированными
данными. Это не означает nullable в мигрированной таблице; expression index
не представлен в Prisma-схеме. Не заменять raw SQL через db push/migrate deploy.

## Проверка

11 SQL-сценариев на отдельных случайных схемах disposable PostgreSQL:
повторное применение, точные суммы/оформление, отказ пяти видов старых данных,
25 пробельных символов и недопустимые символы, конкурентные прямые вставки,
таймаут занятой таблицы, POST/PUT против конкурентного стороннего писателя.
Сравниваются данные и признаки DDL до/после; публичная таблица не мигрируется.
Таблицы синтетические, LIKE с индексами/типами, без FK; это не репетиция
миграции всей производственной схемы или проверки её зависимостей.

76 API/SQL-тестов прошли узко. Общая регрессия 22:53:10: **1072/50/194 SQL**,
48,21 с, один worker, heap 512 MiB, timeout 180 с. Полный TSC, scoped lint и
редактор прошли; два прежних предупреждения конфигурации. Production,
перезапуски, сборки и браузер не использовались.

## Условия Применения

1. Подтвердить БД v2 и целевую схему; выполнить 17 read-only диагностик по
   организациям. Нулевые счётчики не разрешают автоматически миграцию.
2. Разобрать исключения с владельцем учёта, не переименовывать/сливать счета
   автоматически. Подтвердить резервную копию и восстановление.
3. На восстановленной копии проверить реальную схему, зависимости, права,
   длительность блокировки, повторный запуск и API нового кода. При таймауте
   не повышать лимиты автоматически; согласовать отдельный план.
4. Только после релизных ворот применить raw SQL в согласованном окне и
   проверить NOT NULL/CHECK/уникальность, неизменность данных и API. Изменение
   образа обратно не отменяет SQL-ограничения; обратную миграцию не выполнять
   без отдельного решения и остановки записей.

Не реализованы историческая неизменяемость реквизитов в SQL, монотонная версия,
валютный/банковский регистр и оригиналы выписок. Это не полное закрытие
ACC-048, TASK-0005 или G0-G4. Порядок выпуска: [DEPLOYMENT](../DEPLOYMENT.md).
