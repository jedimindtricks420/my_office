# ADR-0001 — Отдельное Next.js-приложение `marketing/` для публичных SEO-страниц

Дата: 2026-09-09. Контекст: [TASK-0003](../../tasks/active/TASK-0003-seo-landings-ru-uz.md).

## Решение

Публичные RU/UZ SEO-страницы (30 тем × 2 языка) реализованы как отдельное
Next.js-приложение `marketing/` внутри `contador_v1`, задеплоенное отдельным
Docker-контейнером (`contador-marketing`, порт 3033) и подключённое к nginx
только через префиксы `/ru/`, `/uz/`, `/_next/`, `/og/`, `/sitemap.xml`,
`/robots.txt`. Корень `/`, `/v2` и `/admin` не изменены.

## Почему не встроили страницы в существующее приложение

На момент начала работы корень `contador.uz` обслуживал статический
одностраничный HTML (`/home/admin1/landing/index.html`) — без фреймворка,
без git, без `sitemap.xml`/`robots.txt`. Это не поддерживаемое приложение, в
которое можно было бы органично добавить 60 маршрутов, локализацию,
manifest-driven роутинг и калькуляторы. `v2` (Next.js, `basePath: /v2`) —
авторизованный кабинет с проверкой сессии почти на всех путях; вставка
публичных страниц туда либо потребовала бы ослаблять проверку сессии для
конкретных путей (риск для приватного контура), либо жить под `/v2/...`, что
противоречит требованию задачи «SEO-URL без `/v2`».

## Почему не редиректнули корень `/` на `/ru/`

Задача (раздел 4) допускала оба варианта в зависимости от того, индексируется
ли корень целенаправленно. Решение владельца продукта (2026-09-09): оставить
текущую статическую главную как есть, не редиректить. Причина не
формализована в коде — фиксируется здесь как принятое решение, а не гипотеза
агента.

## Как это работает в проде

```
nginx (contador.uz, :443)
├── location = /            → статика /home/admin1/landing/  (не менялось)
├── location /v2/           → contador-v2:3032                (не менялось)
├── location /admin         → contador-admin:3031              (не менялось)
├── location /ru/           → contador-marketing:3033  (новое)
├── location /uz/           → contador-marketing:3033  (новое)
├── location /_next/        → contador-marketing:3033  (новое, статика Next)
├── location /og/           → contador-marketing:3033  (новое, OG-картинки)
├── location = /sitemap.xml → contador-marketing:3033  (новое)
└── location = /robots.txt  → contador-marketing:3033  (новое)
```

`marketing/` не импортирует Prisma, не создаёт сессий, не обращается к
приватным финансовым API. Единственный внешний вызов — `GET
http://admin:3031/admin/api/payment-info` (тот же эндпоинт и тот же паттерн
переменной `ADMIN_API_URL`, что уже использует `v2`) за живой ценой тарифа
PRO для `/ru/tarify/`/`/uz/tariflar/`, с фолбэком на константу при
недоступности admin.

`Dockerfile.marketing` — та же трёхстадийная сборка и то же ограничение
памяти (`NODE_OPTIONS=--max-old-space-size=3072`, `next.config.ts`
`experimental.cpus: 1`), что и `Dockerfile.v2`, по той же причине: инцидент
19.08.2026, когда неограниченная сборка `v2` съела всю RAM хоста и уронила
VM. Сборка `marketing` выполнялась строго последовательно, с проверкой
`free -h` до и после каждого запуска; падения хоста не было.

## Два бага, найденные только реальной HTTP-проверкой (не модульными тестами)

Реализация проходила поэтапно (6 контентных фаз), каждая — с модульными
тестами через `renderToStaticMarkup` (прямой вызов серверных компонентов, без
роутинга Next.js и без запущенного процесса — на этом хосте нельзя было
поднимать dev-сервер для проверки на протяжении контентных фаз). Все фазы
проходили тесты/`tsc`/`eslint`/`next build` без ошибок. Тем не менее, при
первом реальном `docker build` + `docker run` + `curl` (стадия деплоя, не
предыдущие стадии) обнаружились два бага, которые модульные тесты в принципе
не могли поймать, потому что они возникают только в реальном роутинге Next.js:

1. **`dynamicParams = false` на опциональном catch-all (`[locale]/[[...slug]]`)
   не регистрировал ни один сгенерированный `generateStaticParams`-путь как
   разрешённый в рантайм-манифесте** в этой сборке (Next.js 16.2.1,
   Turbopack, `output: standalone`) — каждый запрос, включая существующие
   URL, падал с `NoFallbackError` (404 в ответе, ошибка в логах контейнера).
   Исправление: убрали `dynamicParams = false`; сама страница уже вызывает
   `notFound()` для неизвестной локали/слага через `findTopicBySlug`, так что
   настоящий 404 для мусорных путей обеспечивается кодом компонента, а не
   этим флагом маршрутизации.
2. **`/ru/` редиректило на `/ru`** (дефолтный `trailingSlash: false` в
   Next.js), где маршрут не резолвился — при этом весь manifest
   (`lib/manifest.ts`, `urlFor()`) генерирует canonical/hreflang/sitemap/
   внутренние ссылки только с завершающим слэшем. Исправление: явный
   `trailingSlash: true` в `next.config.ts`.

После обоих исправлений — прямой `curl` всех 60 URL из sitemap, сначала на
`localhost:3033` внутри хоста, затем через реальный `https://contador.uz` —
подтвердил 200 на всех 60, корректные hreflang/canonical (абсолютные URL на
`contador.uz`), реальную живую цену на странице тарифов, и настоящий 404 на
мусорных путях/локалях.

**Вывод для будущих задач в этом репозитории**: рендер-тесты через
`renderToStaticMarkup` проверяют, что компонент выдаёт правильный HTML —
но не проверяют, что Next.js-роутинг вообще доведёт запрос до этого
компонента. Для manifest-driven catch-all маршрутов с
`generateStaticParams` обязательна хотя бы одна проверка реальным
собранным контейнером/HTTP-запросом перед объявлением фичи готовой к
продакшену, даже если сама конфигурация сборки (`cpus: 1`, лимит памяти)
не позволяет держать dev-сервер запущенным постоянно.
