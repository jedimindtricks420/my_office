## Условия Следующего Релиза

Прошлый выпуск был отдельно запрошен пользователем; он не закрыл ворота.
Безопасный порядок следующих изменений:

1. Завершить оставшиеся P0, утвердить бухгалтерские контрольные примеры и округление; выполнить аудит данных с ограничениями ниже.
2. Проверить актуальную резервную копию и её восстановление на отдельном стенде. Исторические дампы в backups не доказывают готовность отката.
3. Собрать только v2 на отдельном runner с жёсткими лимитами памяти/CPU и без production-секретов; выполнить HTTP smoke-тесты и интеграционные проверки на копии данных. Зафиксировать image digest и предыдущий образ для отката.
4. Если доступен только этот хост, сначала согласовать окно и общий cgroup-бюджет сборщика. Heap 3072 MB и cpus:1 из Dockerfile/Next не ограничивают весь RSS дерева сборки; mem_limit сервиса ограничивает runtime, а не build. Одного свободного объёма RAM недостаточно; swap отсутствует.
5. Только после ворот и проверенной резервной копии заменить один v2 заранее собранным образом, без сборки и перезапуска зависимостей. Не выполнять общий `docker compose up -d --build`.
6. Проверить вход, членство, обычное проведение, отказ повтора, отмену, отчёты и ошибки календаря. При регрессии остановить новые записи и применить заранее проверенный план отката. Возврат образа не отменяет миграции/изменённые данные.

Четыре перечисленных патча уже применены, не повторять выпуск как новую
миграцию. Для следующих патчей нужны отдельный preflight, проверка порядка
и репетиция на актуальной копии. Аудит/replay исторического учёта не заменён
очисткой организаций или успешным восстановлением backup.

Банковские номера: [ADR-0012](adr/ADR-0012-bank-account-database-identity.md).
Миграция берёт ACCESS EXCLUSIVE до проверки всей таблицы, поэтому также
блокирует чтение; lock_timeout 1 с и statement_timeout 5 с не являются
разрешением на применение в рабочее время. Сначала нужна репетиция на копии
реальных данных и согласованное окно. При старых номерах/дублях миграция
отказывается без исправлений; таймауты автоматически не увеличивать.

### Read-only аудит бухгалтерии

Из `v2/`: `npm run audit:accounting -- --help` либо
`npm run audit:accounting -- <orgId>` при заранее безопасно установленном
`ACC_AUDIT_DATABASE_URL`. Не записывать URL с паролем в журнал/задачу/историю shell;
предпочтительна отдельная read-only роль или восстановленная копия БД.
Скрипт не использует DATABASE_URL как fallback, требует явную организацию.

Одна READ ONLY REPEATABLE READ транзакция: maxWait 5 с, timeout 15 с,
statement_timeout 5 с, lock_timeout 1 с, work_mem 4 MB. Выполнять последовательно
по организациям и прекратить при деградации БД; read-only не означает нулевую нагрузку.
При ошибке/timeout аудит не завершён, результат нельзя считать чистым.

17 счётчиков охватывают пустые/несбалансированные/некорректные проводки,
VOIDED с проводками, дату/период и межорганизационные ссылки, FAILED календаря,
возможные дубли проводок/ИНН, признаки убытка на 9320 и валютного банка на 5110,
необработанные банковские строки закрытого периода и позиции без документа погашения.
Три новых счётчика показывают пустые/неверные номера банковских счетов и
группы дублей внутри организации после той же нормализации, что в API.
Сами номера не выводятся и не исправляются; нулевой отчёт одной организации
не заменяет проверку всей таблицы под блокировкой в миграции.
Эвристические совпадения требуют анализа; нулевые счётчики не заменяют сверку
налогов, маппингов, распределений, валюты и финансовых форм.

## Миграции — порядок применения (реальный, не `prisma migrate deploy`)

Ни admin, ни v2 **не вызывают** `prisma migrate deploy` ни в одном
Dockerfile, ни в одном `package.json`-скрипте. Оба каталога
`*/migrations/` — плоские наборы `.sql`-файлов без стандартной структуры
Prisma (подробности — [DATABASE.md](DATABASE.md)). Наблюдаемый на практике
процесс (по хронологии имён файлов и содержимому README-примечаний в самих
`.sql`, не читанных как источник фактов, а только как метаданные файла):

1. Изменить `schema.prisma`.
2. Написать соответствующий `.sql`-патч вручную, положить в
   `<app>/prisma/migrations/<YYYYMMDD>_<name>.sql`.
3. Сделать резервную копию БД перед применением (см. `backups/` — паттерн
   `contador_v2_pre_<изменение>_<таймштамп>.dump`).
4. Применить `.sql`-файл вручную через `psql` к работающей БД.
5. Убедиться, что `schema.prisma` и реальная структура БД синхронны (нет
   автоматической проверки в CI — не найдено файлов CI/CD в репозитории).
