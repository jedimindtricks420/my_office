Последняя регрессия 11 сентября: 712/19 v2, отдельно 173/7 PostgreSQL

Команды и границы доказательств: [PROGRESS](PROGRESS-2026-09-11.md).
Рабочие сервисы не перезапускались. Текущий disposable PostgreSQL ограничен
384 MiB/0,5 CPU; прежние тестовые контейнеры удалены. Это не копия production.

Безопасный порядок следующего релиза:

1. Завершить оставшиеся P0, утвердить бухгалтерские контрольные примеры и округление; выполнить аудит данных с ограничениями ниже.
2. Проверить актуальную резервную копию и её восстановление на отдельном стенде. Исторические дампы в backups не доказывают готовность отката.
3. Собрать только v2 на отдельном runner с жёсткими лимитами памяти/CPU и без production-секретов; выполнить HTTP smoke-тесты и интеграционные проверки на копии данных. Зафиксировать image digest и предыдущий образ для отката.
4. Если доступен только этот хост, сначала согласовать окно и общий cgroup-бюджет сборщика. Heap 3072 MB и cpus:1 из Dockerfile/Next не ограничивают весь RSS дерева сборки; mem_limit сервиса ограничивает runtime, а не build. Одного свободного объёма RAM недостаточно; swap отсутствует.
5. Только после ворот и проверенной резервной копии заменить один v2 заранее собранным образом, без сборки и перезапуска зависимостей. Не выполнять общий `docker compose up -d --build`.
6. Проверить вход, членство, обычное проведение, отказ повтора, отмену, отчёты и ошибки календаря. При регрессии остановить новые записи и применить заранее проверенный план отката. Возврат образа не отменяет миграции/изменённые данные.

Подготовлены raw SQL-миграции Soliq batch, банковских номеров и банковского
архива, но готового
релизного образа нет; backup/restore, production-аудит и HTTP smoke-тесты нового
кода ещё не проверены. Soliq проверен на disposable-БД, банковские ограничения
только на изолированных синтетических таблицах. Миграции нельзя применять
пакетом без отдельного preflight и проверки порядка.

Банковский архив: [ADR-0014](adr/ADR-0014-bank-import-source-archive.md).
Новый import/rollback требует таблицу BankImportBatch: raw SQL
`v2/prisma/migrations/20260911_bank_import_batch.sql` применяется до запуска
нового кода, Prisma Client генерируется из соответствующей схемы.
Миграция и её повтор проверены только в disposable-БД, не на копии production.
Lock timeout 1 с, statement timeout 10 с; RESTRICT запрещает удалять счёт
или организацию с архивом. Нужны репетиция, backup/restore, лимиты хранения
и контролируемая пауза банковских записей. Старый образ не обновляет статус
нового архива при откате; возвращать его с открытыми банковскими записями
без сверки нельзя. Не удалять таблицу с оригиналами для возврата кода.

Банковские номера: [ADR-0012](adr/ADR-0012-bank-account-database-identity.md).
Миграция берёт ACCESS EXCLUSIVE до проверки всей таблицы, поэтому также
блокирует чтение; lock_timeout 1 с и statement_timeout 5 с не являются
разрешением на применение в рабочее время. Сначала нужна репетиция на копии
реальных данных и согласованное окно. При старых номерах/дублях миграция
отказывается без исправлений; таймауты автоматически не увеличивать.

### Read-only аудит бухгалтерии

Из `v2/`: `npm run audit:accounting -- --help` либо
`npm run audit:accounting -- <orgId>` при заранее безопасно установленном
`ACC_AUDIT_DATABASE_URL`. Не записывать URL с паролем в журнал/задачу/историю shell;
предпочтительна отдельная read-only роль или восстановленная копия БД.
Скрипт не использует DATABASE_URL как fallback, требует явную организацию.

Одна READ ONLY REPEATABLE READ транзакция: maxWait 5 с, timeout 15 с,
statement_timeout 5 с, lock_timeout 1 с, work_mem 4 MB. Выполнять последовательно
по организациям и прекратить при деградации БД; read-only не означает нулевую нагрузку.
При ошибке/timeout аудит не завершён, результат нельзя считать чистым.

17 счётчиков охватывают пустые/несбалансированные/некорректные проводки,
VOIDED с проводками, дату/период и межорганизационные ссылки, FAILED календаря,
возможные дубли проводок/ИНН, признаки убытка на 9320 и валютного банка на 5110,
необработанные банковские строки закрытого периода и позиции без документа погашения.
Три новых счётчика показывают пустые/неверные номера банковских счетов и
группы дублей внутри организации после той же нормализации, что в API.
Сами номера не выводятся и не исправляются; нулевой отчёт одной организации
не заменяет проверку всей таблицы под блокировкой в миграции.
Эвристические совпадения требуют анализа; нулевые счётчики не заменяют сверку
налогов, маппингов, распределений, валюты и финансовых форм.

## Установка и локальный запуск (выведено из `package.json`/Dockerfile — сам процесс не выполнялся)

Требования: Node.js **20**, PostgreSQL **16**, npm.

### admin (порт 3031)

```bash
cd /home/admin1/contador
npm install
npx prisma generate                                    # схема prisma/schema.prisma → contador
npx prisma generate --schema ../v2/prisma/schema.prisma # доп. клиент → contador_v2 (тот же процесс читает обе БД)
# ⚠️ прямого скрипта npm start НЕТ — package.json не содержит секции "scripts"
npx tsx admin/server.ts
```

Обязательные переменные окружения: `DATABASE_URL`, `V2_DATABASE_URL`,
`ADMIN_PASSWORD` (см. [CONFIGURATION.md](CONFIGURATION.md) — оба явно
проверяются кодом при старте и роняют процесс при отсутствии).

### v2 (порт 3032, basePath `/v2`)

```bash
cd /home/admin1/contador/v2
npm install
npm run db:generate     # prisma generate
npm run db:push         # применяет ТЕКУЩУЮ схему целиком (создание БД с нуля) —
                         #   НЕ то же самое, что применение 9 инкрементальных .sql-патчей,
                         #   см. ниже «Миграции»
npm run dev              # next dev -p 3032   (или: npm run build && npm run start)
```

При каждом старте (`dev`/`start`/production-рантайм) автоматически
выполняется `instrumentation.ts` → `ensureBaseData()` — сидинг 269 счетов
плана НСБУ и 180 типов документов происходит **сам**, отдельного шага
«накатить сид-данные» не требуется и не существует.

Обязательная переменная: `JWT_SECRET` (роняет процесс при отсутствии, см.
CONFIGURATION.md). `DATABASE_URL` — Prisma упадёт при первом обращении к БД
без неё.

## Миграции — порядок применения (реальный, не `prisma migrate deploy`)

Ни admin, ни v2 **не вызывают** `prisma migrate deploy` ни в одном
Dockerfile, ни в одном `package.json`-скрипте. Оба каталога
`*/migrations/` — плоские наборы `.sql`-файлов без стандартной структуры
Prisma (подробности — [DATABASE.md](DATABASE.md)). Наблюдаемый на практике
процесс (по хронологии имён файлов и содержимому README-примечаний в самих
`.sql`, не читанных как источник фактов, а только как метаданные файла):

1. Изменить `schema.prisma`.
2. Написать соответствующий `.sql`-патч вручную, положить в
   `<app>/prisma/migrations/<YYYYMMDD>_<name>.sql`.
3. Сделать резервную копию БД перед применением (см. `backups/` — паттерн
   `contador_v2_pre_<изменение>_<таймштамп>.dump`).
4. Применить `.sql`-файл вручную через `psql` к работающей БД.
5. Убедиться, что `schema.prisma` и реальная структура БД синхронны (нет
   автоматической проверки в CI — не найдено файлов CI/CD в репозитории).

## Docker Compose — оркестрация продакшна

`docker-compose.yml` (корень) — 4 сервиса, сеть `contador-net` (bridge):

| Сервис | Образ | Порт | depends_on |
|---|---|---|---|
| `db` | `postgres:16-alpine` | не публикуется (`expose: 5432`) | — |
| `admin` | `Dockerfile.admin` | `3031:3031` | `db` (healthy) |
| `v2` | `Dockerfile.v2` | `3032:3032` | **нет** `depends_on` на `db` |
| `marketing` | `Dockerfile.marketing` | `3033:3033` | `admin` |

`v1` не описан в compose-файле вовсе.

**`marketing`** добавлен 2026-09-09 (`TASK-0003`) — публичные SEO-лендинги
RU/UZ, отдельное Next.js-приложение (`marketing/`, без Prisma/сессий/БД).
Единственная сетевая зависимость — цена тарифа PRO на `/ru/tarify/` и
`/uz/tariflar/`, читается с `http://admin:3031/admin/api/payment-info` по
имени сервиса в `contador-net` (`ADMIN_API_URL` — та же переменная и тот же
паттерн, что и в `v2/.env`; **не** `localhost`, внутри контейнера это сам
контейнер). Nginx (`/etc/nginx/sites-available/contador.uz`) проксирует
`/ru/`, `/uz/`, `/_next/`, `/og/`, `= /sitemap.xml`, `= /robots.txt` на
`localhost:3033`; корневой `location /` (статическая `/home/admin1/landing/`)
и `/v2`, `/admin` не менялись.

Общая команда `docker compose up -d --build`, ранее приведённая здесь по
структуре файла, не является безопасной инструкцией для текущего хоста.
Для TASK-0005 действует порядок ограниченного выпуска выше.

`Dockerfile.v2` — многостадийная сборка (`deps` → `builder` → `runner`),
`NODE_OPTIONS="--max-old-space-size=3072"` и `next.config.ts`'s
`experimental.cpus: 1` — оба ограничения явно прокомментированы в коде как
последствие инцидента **19.08.2026**, когда неограниченная сборка исчерпала
всю память хоста без свопа и уронила VM (`Dockerfile.v2`, комментарий перед
`ENV NODE_OPTIONS`). `docker-compose.yml`'s `mem_limit: 1g` /
`mem_reservation: 256m` на сервисе `v2` — та же защита для рантайма.
