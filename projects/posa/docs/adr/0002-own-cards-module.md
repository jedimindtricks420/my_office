# ADR-0002. «Мои карты» — отдельный модуль, модерация по отпечатку редакции, сертификаты вендоров

Дата: 2026-11-05
Статус: принято, реализовано (коммит `6d6cae5` в `POSA-v3`)

## Контекст

Владелец хочет, чтобы вендоры сами выпускали брендированные карты Apple Wallet
и Google Wallet, выдавали их клиентам и рассылали уведомления
([заметка владельца](../OWNER_NOTE_VENDOR_WALLET_PASSES.md)). Три требования
определили устройство:

1. Нельзя затронуть прежние ваучеры, продажи, выплаты и кассы.
2. Рассылка уходит клиентам только после утверждения администратором Namo —
   именно той редакции, которую он видел.
3. Карты могут подписываться сертификатом вендора, а не только сертификатом
   Namo.

## Решения

### 1. Отдельный модуль в том же приложении

Свои таблицы `Own*`, свои роуты (`/vendor/own-vouchers`, `/v/…`,
`/v/wallet/…`, `/admin/own-cards…`) и сервисы `services/ownVouchers/`.
Связей с `Voucher`, `Product`, `Sale` и денежными таблицами нет. На кассе код
сначала ищется среди `OwnVoucher`; не найден — прежний поток без изменений.

Включение двумя выключателями: глобальный флаг `OWN_VOUCHERS_ENABLED` (без
него роуты не монтируются) и флаг вендора в `VendorOwnVoucherSettings`.

Отдельный процесс, как у Paynet ([ADR-0001](0001-paynet-channel-as-separate-process.md)),
не нужен: модуль использует сессии, роли и кабинет вендора основного
приложения, отдельного внешнего протокола нет.

### 2. Одобрение привязано к отпечатку редакции

`broadcastHash` = sha256 от программы, сегмента и текста. При одобрении
сохраняется `approvedHash` и срок `approvalExpiresAt` (7 дней). Отправка
разрешена только в статусе `APPROVED` при совпадении текущего отпечатка с
одобренным и не истёкшем сроке. Любая правка сбрасывает одобрение. Форма
администратора передаёт отпечаток показанной ему редакции — если вендор
изменил текст, пока администратор читал, решение отклоняется. Изменения
рассылок одной программы идут под `pg_advisory_xact_lock`. Получатели
считаются в момент отправки, а не при одобрении.

Отвергнуто: «одобрение по id рассылки» — вендор мог бы изменить текст после
одобрения.

### 3. Сертификат вендора хранится в базе, карта помнит свой Pass Type ID

Сертификат и закрытый ключ хранятся в `OwnAppleCertificate`; ключ — только
зашифрованным AES-256-GCM, ключ шифрования выводится из `OWN_CERT_SECRET`
(переменная окружения, не в базе). Каждая карта хранит `applePassTypeId`,
которым подписана; обновления и push идут подписантом этой карты. Без
сертификата вендора используется сертификат Namo из окружения.

Следствия:

- замена сертификата вендора не ломает выданные карты;
- сертификат, которым подписаны карты, удалить нельзя — только отключить;
- потеря или смена `OWN_CERT_SECRET` делает сохранённые ключи нечитаемыми:
  переменную нужно хранить вместе с резервными копиями базы.

### 4. Кнопка кошелька по устройству; Google — через API и уведомления о сохранении

Дополнено 2026-11-05 (коммит `ac33f8d`). Google Wallet на Android импортирует файл
Apple `.pkpass`, но такая копия статична: сервис обновлений Apple Google не вызывает,
рассылки до неё не доходят, а система не знает, что карта сохранена. Поэтому:

- страница карты показывает только кнопку своего устройства; Android файл Apple не
  получает;
- карта Google создаётся через Wallet API до перехода в Google, в ссылке — только
  идентификатор; обновления — `PATCH`, чтобы не стирать сообщения рассылок;
- «в кошельке на Android» — только по подписанному уведомлению Google о сохранении
  (`OwnVoucher.googleSavedAt`), а не по факту открытия ссылки.

Отвергнуто: оставить файл Apple для Android как запасной путь — клиент получал бы
карту, которая выглядит рабочей, но никогда не обновляется.

## Последствия

- Откат модуля — снять `OWN_VOUCHERS_ENABLED`: таблицы остаются, прежний
  функционал от них не зависит.
- Роли кассира (`OwnStaffRole`) действуют только внутри «Моих карт»;
  остальной кабинет вендора по-прежнему не различает роли.
