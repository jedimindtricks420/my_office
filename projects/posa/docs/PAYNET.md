# PAYNET — канал продаж через терминалы партнёрских сетей

Последнее обновление: 2026-10-24. Источник фактов — код в
`/opt/apps/posa/activation-system/` (после миграции на Alibaba; в ранних
документах путь указан как `/home/admin1/posa/`) и официальный тестер Paynet.

## Что это

Третий канал продаж POSA, наряду с QR-ссылкой мерчанта и витриной магазина.
Клиент покупает ваучер **в терминале или приложении Paynet**, а не на наших
страницах. Выдача ваучера, SMS и попадание в Namo Wallet происходят так же,
как при покупке по QR, потому что все каналы используют одну и ту же функцию
выдачи `processPaymentInternal`.

Реализован по спецификации «Универсальный WEB-сервис поставщика услуг»
(UWS) версии 1.0, JSON-RPC 2.0 поверх HTTPS POST.

## Чем принципиально отличается от Click, Payme и Alifpay

Направление вызовов обратное:

| | Click / Payme / Alifpay | Paynet (UWS) |
|---|---|---|
| Кто инициирует | мы создаём счёт и уводим клиента | Paynet обращается к нам |
| Кто выдаёт логин и пароль | провайдер нам | **мы провайдеру** |
| Где находится клиент | на наших страницах | в терминале партнёра |
| Заказ до оплаты | создаётся нами заранее | не существует |

Из этого следует главное ограничение: `PerformTransaction` **синхронный**.
Paynet по ответу решает, списывать деньги или нет. Поэтому ваучер должен
быть реально выдан **до** того, как мы ответим «успех».

## Сценарий в терминале

1. Клиент выбирает услугу — это **бренд**: «Microsoft», «Dr.Web», «Roblox».
2. Терминал запрашивает список позиций: `GetInformation` без кода товара.
3. Клиент выбирает позицию. Терминал запрашивает цену и наличие:
   `GetInformation` с кодом.
4. Клиент вводит номер телефона.
5. Клиент платит. Терминал вызывает `PerformTransaction`.
6. Мы выдаём ваучер, отправляем SMS, кладём в кошелёк и только потом
   отвечаем `providerTrnId`.
7. Клиент входит в Namo Wallet по своему номеру и видит ваучер.

## Endpoint и авторизация

```
POST /api/payments/uws/paynet
Content-Type: application/json
Authorization: Basic <login:password>
```

Логин и пароль задаются на услугу в админке и хранятся **bcrypt-хешем**:
подпись считать не нужно, достаточно проверки. Неверная или отсутствующая
пара — строго **HTTP 401**, а не JSON-RPC ошибка.

Запрос не методом POST — ошибка `-32300`.

## Методы

| Метод | Назначение | Ключевое поведение |
|---|---|---|
| `GetInformation` | каталог услуги либо цена и наличие позиции | `status` — **строка** |
| `PerformTransaction` | провести оплату и выдать ваучер | повтор `transactionId` → **201** |
| `CheckTransaction` | статус операции | не найдена → `203` либо `transactionState: 3` |
| `CancelTransaction` | отмена | повторная отмена → `202` |
| `GetStatement` | реестр за период | **только успешные**, `amount` в тийинах |
| `ChangePassword` | не реализован | `-32601`, метод в спецификации необязательный |

## Контракт, выверенный по официальному тестеру

Тестер Paynet строже текста спецификации. Расхождения, где прав тестер:

- `status` в `GetInformation` — **строка** (`"0"`), хотя таблица в
  спецификации говорит Number.
- `timestamp` строго `yyyy-MM-dd HH:mm:ss` в GMT+5. Пример
  `"Tue Dec 30 10:29:03 UZT 2025"` из спецификации неверен; на входе мы
  принимаем оба формата, на выходе отдаём только первый.
- В `CheckTransaction` и `CancelTransaction` приходит поле `timestamp`,
  хотя таблицы спецификации называют его `transactionTime`.
- `transactionId` — до 15 цифр, больше 2³¹. Хранится как `BigInt`.
- `fields` в ответе `PerformTransaction` **обязателен**.
- Повторный `PerformTransaction` с тем же `transactionId` должен вернуть
  **ошибку 201**, а не повторить прежний успех. Реальный статус партнёр
  выясняет через `CheckTransaction`.
- Неудачный `PerformTransaction` **не должен регистрировать**
  `transactionId`: тестер присылает неудачные попытки с тем же
  идентификатором, что и последующую успешную.
- В `GetStatement` отменённых транзакций быть не должно.

### Режим тестирования

У тестера четыре режима, и модели «продажа товаров» соответствует только
один — **многоразовые платежи, отмена не используется** (13 проверок).
Остальные требуют либо числового баланса в `fields`, либо «закрытия
клиента» после оплаты — ни то, ни другое к продаже товаров не применимо.
Если Paynet по договору потребует `CancelTransaction`, подходящего режима
в их инструменте нет, и это надо согласовывать отдельно.

## Коды ошибок

Используются коды из §2.5 спецификации:

| Код | Когда возвращаем |
|---|---|
| `-32300` | запрос не методом POST |
| `-32700` | тело не разбирается как JSON |
| `-32601` | неизвестный метод |
| `100` | позиция настроена некорректно (цена не кратна шагу) |
| `101` | ваучеры по позиции закончились |
| `201` | `transactionId` уже проводился |
| `202` | транзакция уже отменена |
| `203` | транзакция не найдена |
| `301` | номер телефона не проходит валидацию |
| `304` | код позиции не найден в услуге |
| `305` | `serviceId` не совпадает с услугой авторизации |
| `413` | сумма не равна цене канала |
| `414` | не разбирается дата в `GetStatement` |

## Схема данных

```
PartnerService ─ услуга = бренд в меню терминала
   partner · serviceId · name · login · passwordHash · isActive
   ├── kassaId ─────▶ Kassa      контракт, по которому приходят деньги
   ├── merchantId ──▶ Merchant   технический мерчант канала
   └── items
        └── PartnerServiceItem ─ позиция в списке товаров
               code · label · priceOverride · sortOrder · isActive
               └── productId ──▶ Product ──▶ Vendor ──▶ Voucher (пул кодов)

PartnerTransaction ─ журнал канала, он же источник providerTrnId
   partner + externalTxnId  ◀── уникальный индекс
   code · phone · amount · state (1 проведена / 2 отменена)
   saleId · voucherValue · createdAt · cancelledAt
```

`PartnerService` намеренно **не привязан к вендору**: услуга в терминале —
это витрина, а не учётная запись поставщика. Благодаря этому вендор
ManaMinds раскладывается на две услуги — «PUBG Mobile» и «Roblox».

`merchantId` обязателен. Без него продажа из терминала могла бы
зачислиться случайному мерчанту того же товара, у которого есть своя
QR-привязка.

## Цены

Цена канала определяется так:

```
priceOverride позиции  →  иначе Product.price
         ↓
кратна 10 000 сум?
   да  → отдаём терминалу (сумы и тийины)
   нет → позиция скрыта из каталога, оплата отклоняется кодом 100
```

Шаг 10 000 сум продиктован тем, что **в терминалах не дают сдачи**, а
купюры в обороте кратны десяти тысячам. При создании и изменении товара
кратность проверяется; правило применяется только к **новой** цене, чтобы
товары, заведённые раньше, оставались редактируемыми.

Базовая цена товара каналом не меняется: в вебе и по QR цены прежние.

## Выдача ваучера

`PerformTransaction` вызывает `processPaymentInternal` — ту же функцию, что
Click, Payme и Alifpay. Внутри одной транзакции базы:

1. взять свободный ваучер (атомарный claim с проверкой `count`);
2. пометить проданным;
3. записать `Sale` — цена равна **фактически списанной сумме**;
4. найти или создать клиента по номеру телефона;
5. положить ваучер в кошелёк (`OnlineVoucher`, `VoucherWalletLog`);
6. начислить комиссии вендору, мерчанту и кассе;
7. обновить балансы и счётчик `Kassa.totalReceivedPaynet`.

После коммита, уже не влияя на исход продажи: PDF-чек и SMS.

## Защиты

| Риск | Механизм |
|---|---|
| Один ваучер двум клиентам | атомарный claim + одна повторная попытка |
| Повторная выдача при ретрае | уникальный индекс `(partner, externalTxnId)` |
| Неверная сумма от терминала | сверка с ценой канала, иначе `413` |
| Продажа ушла чужому мерчанту | привязка строго к `PartnerService.merchantId` |
| Некорректно настроенная цена | предохранитель: позиция скрыта, оплата `100` |
| Чужой телефон или код | валидация кода оператора (`301`), каталога (`304`) |
| Креды одной услуги на другой | сверка `serviceId` с авторизацией (`305`) |

## Развёртывание

Шлюз вынесен **отдельным процессом с той же кодовой базой и той же базой
данных**: поток из терминалов не делит процесс с кошельком и
перезапускается независимо, но выдача остаётся атомарной.

- точка входа — `uws-server.js`, открыты только роуты UWS;
- сервис `uws` в `docker-compose.yml`, контейнер `activation-uws`;
- слушает `0.0.0.0:4010` внутри контейнера, порт опубликован как
  `127.0.0.1:4010` — изоляция обеспечивается привязкой к loopback;
- проверка живости: `GET /healthz`.

### Что осталось сделать до приёма боевого трафика

1. Поддомен и TLS-сертификат для шлюза, проксирование в nginx на
   `127.0.0.1:4010`.
2. Allowlist IP-адресов Paynet в nginx.
3. Завести услуги с настоящими `serviceId` от Paynet и выдать им пары
   логин/пароль.

## Админка

Раздел «Интеграции → Партнёрские сети»:

- `/admin/partners` — услуги: остаток, число продаж, выключатель;
- `/admin/partners/:id/items` — позиции: код, название для клиента, товар,
  цена канала, остаток, порядок, выключатель;
- `/admin/partner-journal` — журнал транзакций с фильтрами по услуге,
  статусу, телефону и датам, для сверки с реестром партнёра.

Доступ: роли `admin`, `financial_mgr`, `content_mgr`.

## Открытые вопросы к Paynet

Блокируют финальную настройку, но не разработку:

1. Умеет ли терминал получать список позиций динамически из
   `GetInformation`, или список прошивается на их стороне?
2. Берёт ли терминал сумму из нашего ответа, или она настраивается у них?
3. Какие имена ключей в `fields`? Сейчас ожидаем `phone` и `code`,
   переопределяются через `UWS_FIELD_PHONE` и `UWS_FIELD_CODE`.
4. Нужна ли отмена, и какой код возвращать, если ваучер уже открыт
   клиентом? В §2.5 подходящего кода нет.

Полный список вопросов согласуется отдельно.

## Известные ограничения

- **Откат выдачи при отмене не реализован.** `CancelTransaction` помечает
  транзакцию канала отменённой, но ваучер, продажу и балансы не
  откатывает: политика отмены уже выданного кода не согласована (вопрос 4).
- **Вендоры с выдачей по запросу** (Dr.Web, ManaStore, Rokky) отдают код в
  момент открытия ваучера в кошельке. Если их API недоступен, клиент из
  терминала получит SMS, откроет кошелёк и кода не увидит. Для розничного
  канала это требует мониторинга или предзагруженного пула.
