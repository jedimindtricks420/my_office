# OPEN QUESTIONS — keyspro_auto_sender

Последнее обновление: 2026-09-05 (TASK-0001). Список того, что не удалось
подтвердить напрямую кодом/конфигурацией в рамках первичного исследования,
или где найдено расхождение между источниками/находки безопасности.

## Критично — безопасность

1. **Живой GitHub Personal Access Token в открытом виде.** `git remote -v`
   в `/home/admin1/keyspro_auto_sender/` показывает, что URL `origin`
   (`https://<token>@github.com/jedimindtricks420/keyspro_auto_sender.git`)
   содержит PAT непосредственно в строке подключения — это хранится в
   локальном `.git/config` на хосте (не в файлах репозитория и не в
   истории коммитов, насколько проверено). Токен НЕ скопирован ни в один
   файл `my_office` и не должен копироваться. Требуется: проверить область
   действия токена, ротировать его и заменить способ аутентификации git
   (SSH-ключ или credential helper) — это действие по исправлению, вне
   рамок задачи документирования.
2. **`WEBHOOK_SECRET` объявлен, но не проверяется в коде.** Эндпоинт
   `POST /api/v1/process-order` принимает и обрабатывает любой
   синтаксически корректный JSON без проверки подписи/секрета от
   WooCommerce, несмотря на то что и `.env`-пример в README, и сама
   переменная в `Settings` предполагают такую проверку. Подтверждено:
   `grep -rn WEBHOOK_SECRET app/` находит только объявление поля. Не
   выяснено: проверка была удалена в рефакторинге, никогда не
   реализовывалась, или ожидается на уровне Nginx (в текущем конфиге
   Nginx такой проверки тоже нет).
3. **Порт 8000 опубликован на `0.0.0.0`** (не только `127.0.0.1`) —
   единственная защита от прямого доступа, минуя Nginx/TLS, — это
   отсутствие маршрутизации на уровне firewall хоста, которое не
   проверялось в рамках задачи.

## Технические неопределённости

4. **Модель `Product` не используется.** Определена в
   `app/database/models.py`, таблица создаётся, но нигде не читается и не
   пишется — весь дашборд и обработчик заказов используют
   `product_config.json`. Не выяснено: миграция на БД планировалась и не
   завершена, или это осознанно оставленный, но неактивный код.
5. **SQLite-файл `keyspro.db` не персистентен** между пересозданиями
   контейнера (не примонтирован как volume в `docker-compose.yml`). Не
   выяснено, известно ли это ограничение владельцу проекта и является ли
   потеря истории заказов приемлемым риском, или это недосмотр.
6. **Второй git remote `new` →
   `github.com/jedimindtricks420/POSA-v3.git`** в этом же репозитории
   (`keyspro_auto_sender`) — POSA-v3 является отдельным, уже
   задокументированным проектом (`my_office/projects/posa/`). Не
   выяснено, как и зачем этот remote оказался добавлен именно здесь
   (возможно, случайность при копировании конфигурации git между
   проектами на этом хосте).
7. **Пустые дублирующие шаблоны в корневом `templates/`.**
   `templates/complex_product_template.html` и
   `templates/simple_product_template.html` (в корне проекта) — оба 0
   байт, при этом одноимённые файлы в `app/templates/` содержат реальную
   разметку и фактически используются кодом (`Notifier` берёт шаблоны из
   `app/templates/`, не из корневого `templates/`). Не выяснено:
   корневой `templates/` — остаток от более раннего рефакторинга
   структуры проекта, задел на будущее, или ошибочно оставленные файлы.
8. **Назначение `location /partner_bot/`** в Nginx-конфиге
   `webhook.keyspro.uz`, проксирующего на отдельный backend
   `127.0.0.1:8080` — не исследовалось (нет соответствующего кода в этом
   репозитории), не выяснено, является ли это частью экосистемы
   KeysPro.uz или полностью независимым сервисом, разделяющим домен по
   историческим причинам.
9. **Актуальность README.** Указана дата "Последнее обновление:
   2026-01-23", но история git содержит более поздние коммиты (включая
   `e7900be "added dr.web"` от 2026-03-26 и два коммита в мае 2026) —
   секция README про `product_config.json`/Dr.Web не проверялась построчно
   на полное соответствие текущему коду, читалась выборочно как контекст.
10. **Конкурентность Pyrogram-запросов.** `KeyProvider.get_key` шлёт
    команду боту и ждёт 60 секунд перед парсингом ответа по истории чата
    того же диалога — при одновременной обработке двух заказов с
    компонентами через Telegram-путь не выяснено (не тестировалось
    запуском), есть ли риск перепутать/потерять ключ из-за гонки за одной
    и той же историей сообщений одного чата.
11. **Отсутствие тестов и CI** — не выяснялось, есть ли ручное
    тестирование/чек-лист перед деплоем (README не описывает такую
    процедуру), только зафиксирован факт отсутствия автоматизации.
