## 2. Реализовано частично

Код существует и в целом работает, но с оговорками, несостыковками или
недостижимыми ветками.

### 2.1. Пул лицензий `ProductLicense` наполняется, но никогда не расходуется

- `services/order.service.js:20` — функция `assignLicensesToOrder(tx, order)`
  читает `ProductLicense` со статусом `AVAILABLE` и переводит их в `ASSIGNED`.
- Импортируется в `routes/api/admin/index.js:9`
  (`import { ..., assignLicensesToOrder } from '../../../services/order.service.js'`).
- **Нигде не вызывается** — подтверждено `grep -rn "assignLicensesToOrder("`
  по всему дереву: единственные два вхождения — определение и импорт.
- Реальная выдача ключей идёт другим путём:
  `POST /api/admin/orders/:id/lines/:lineId/licenses`
  (`routes/api/admin/index.js:605-618`) создаёt `OrderLineLicense` напрямую,
  без обращения к пулу `ProductLicense`.
- Итог: `POST /api/admin/products/:id/licenses` позволяет наполнить пул
  ключами, но эти данные ни на что не влияют — заказы их не используют.

### 2.2. Журнал аудита пишется в схему, но не заполняется кодом

- Модель `AuditLog` определена (`prisma/schema.prisma:389-400`), читается на
  странице `GET /admin/audit` (`routes/admin.routes.js:197-207`,
  `views/admin/audit.ejs`).
- Функция записи `logAudit()` определена и полностью рабочая
  (`services/audit.service.js:3-18`), у неё есть все необходимые параметры
  (userId, action, entityType, entityId, metadata, ipAddress).
- **`logAudit(` нигде не вызывается** — подтверждено `grep -rn "logAudit("`:
  единственное вхождение — само определение функции. Ни один
  роут/сервис её не импортирует.
- Итог: страница `/admin/audit` в текущем коде **всегда** покажет пустую
  таблицу («Журнал пуст», `views/admin/audit.ejs:31-33`) — записи в
  `AuditLog` неоткуда взяться.

### 2.3. Отсутствует серверная валидация при создании клиента администратором

- `middleware/validate.js:41-50` определяет `schemas.createCustomer`
  (Joi: email, пароль ≥10 символов с буквой+цифрой, ИНН ровно 9 цифр, МФО 5
  цифр, расчётный счёт 20 цифр).
- `POST /api/admin/customers` (`routes/api/admin/index.js:111`) **не
  подключает `validate(schemas.createCustomer)`** — единственная проверка
  на сервере — `bcrypt.hash` (не валидирует формат) и перехват ошибки
  Prisma `P2002` (уникальность email/ИНН) в `catch`.
- Клиентская валидация есть (`views/admin/customer-new.ejs:110-138`, ручные
  `if`-проверки в JS), но это не защита — обходится прямым запросом к API.
- Итог: через прямой вызов API можно создать клиента с ИНН не из 9 цифр,
  МФО произвольной длины и т.д. — схема для этого написана, но не включена.

### 2.4. Расхождение комментария и реального поведения: скачивание файла КП

- `routes/api/quotes.api.js:147` — комментарий "Скачать файл по токену (без
  авторизации — токен является ключом)".
- Фактически роутер `quotesApiRoutes` монтируется в `index.js:134` как
  `app.use('/api/quotes', requireAuth, quotesApiRoutes)` — то есть
  `GET /api/quotes/download/:token` **требует активную сессию**, вопреки
  тексту комментария. Не критично для безопасности (доступ уже
  дополнительно ограничен), но комментарий вводит в заблуждение о модели
  доступа.

### 2.5. Несогласованная валидация пароля на клиенте и сервере

- `views/auth/reset-password.ejs:42,50` — поля `newPassword`/
  `confirmPassword` имеют `minlength="8"`.
- `middleware/validate.js:56-61` (`schemas.resetPassword`) требует
  `Joi.string().min(10).pattern(/[A-Za-z]/).pattern(/[0-9]/)` — минимум 10
  символов, обязательно буква и цифра.
- Итог: пароль, прошедший клиентскую проверку (8 символов, могут быть
  только цифры), гарантированно будет отклонён сервером с 400 — рабочая,
  но противоречивая пара проверок (не баг безопасности, а лишний шаг для
  пользователя).

### 2.6. Отсутствуют проверки на существование заказа перед обращением к его полям

- `routes/api/admin/index.js:531-537` (`POST /orders/:id/cancel`):
  ```js
  const order = await prisma.order.findUnique({ ... });
  if (order.status === 'DELIVERED' || order.status === 'CANCELLED') { ... }
  ```
  Нет проверки `if (!order)` перед обращением к `order.status` — на
  несуществующем `orderId` упадёт `TypeError: Cannot read properties of
  null`, будет поймано общим `catch` → `next(err)` → `errorHandler` вернёт
  500 вместо ожидаемого 404.
- `routes/api/admin/index.js:556-567` (`PATCH /orders/:id/status`) — то же:
  `const customerEmail = order?.customer?.user?.email;` использует
  опциональную цепочку для `order`, но несколькими строками ниже
  `if (order.status !== 'IN_PROGRESS' ...)` уже без неё — непоследовательно,
  тот же риск 500 вместо 404.
- Для сравнения, соседний эндпоинт `POST /orders/:id/deliver`
  (`routes/api/admin/index.js:500-507`) делает проверку `if (!order) return
  res.status(404)...` правильно — расхождение в подходе внутри одного файла.

### 2.7. Миграции Prisma разошлись со схемой — таблицы КП не покрыты ни одной миграцией

- В `prisma/schema.prisma` определены модели `QuoteRequest`, `QuoteDocument`,
  `QuoteDownloadToken` (строки 322-370).
- В `prisma/migrations/` — всего 3 миграции (`20260608201128_init`,
  `20260613000000_add_payment_document_type`,
  `20260613100000_add_fk_indexes`). **Ни одна не создаёт** таблицы
  `quote_requests`/`quote_documents`/`quote_download_tokens` — подтверждено
  `grep -ri "quote"` по всем файлам `migration.sql`, совпадений нет.
- Ни `Dockerfile`, ни `docker-compose.yml`, ни `package.json` **не вызывают
  `prisma migrate deploy`** ни на одном этапе сборки/запуска (`Dockerfile`
  делает только `npx prisma generate` — генерацию клиента, не применение
  миграций к БД).
- Итог: либо таблицы КП были созданы вручную/через `prisma db push` в обход
  системы миграций (тогда `prisma/migrations/` не отражает реальную историю
  схемы БД), либо — если это не так — эндпоинты `/api/quotes/*` и вся
  функциональность КП должны падать на несуществующих таблицах в любой
  свежеразвёрнутой копии БД, поднятой строго по `prisma/migrations/`. Какой
  из двух вариантов верен для текущей прод-БД, кодом не проверяется —
  см. [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md).

### 2.8. `docker-compose.dev.yml` описывает не полное dev-окружение

- Содержит только сервис `db` (Postgres на `5437`) — сервис `app`
  отсутствует. `npm run dev` (nodemon) должен запускаться вне Docker,
  подключаясь напрямую к этой БД — не описано отдельно ни в каком runbook
  внутри самого `mibt-2`.

## Риски безопасности, выявленные при построчном чтении (сверх ранее задокументированных)

- **`public/test-products.html` публично доступен без аутентификации** —
  минорная утечка информации о макете/брендинге, не содержит секретов, но
  не должен быть в проде (см. «Мёртвый код» п. 8).
- **`POST /api/admin/customers` не валидирует ИНН/МФО/расчётный счёт на
  сервере** (см. п. 2.3) — при обходе UI можно создать некорректные
  реквизиты клиента, которые затем попадут в PDF-спецификации
  (`services/pdf.service.js`) и письма.
- **Отсутствие проверки `!order`** (п. 2.6) — не эксплуатируемая уязвимость
  сама по себе, но приводит к утечке деталей ошибки в dev-режиме
  (`middleware/errorHandler.js:15` возвращает `err.stack` в JSON, если
  `NODE_ENV === 'development'`) при обращении к несуществующему `orderId`.
- CSRF (см. «Не реализовано» п. 3) и отсутствие ротации `ADMIN_PASSWORD` по
  умолчанию в `prisma/seed.js:10` (`'AdminPass123!'`, если переменная
  окружения не задана) — уже подробно описаны в `AGENTS.md`/`STATUS.md` по
  предыдущему аудиту, повторно подтверждены в этом.
