# OVERVIEW — MIBT

Последнее обновление: 2026-09-05 (первичное исследование, TASK-0001).

## Что это

Закрытая **B2B/B2G ИТ-платформа** для продажи корпоративным и государственным
заказчикам в Узбекистане лицензий на ПО и оборудование через личный кабинет с
корпоративным балансом. Владелец продукта, согласно seed-данным и email-шаблонам
— компания **GP TECH UNION** (наименование зафиксировано в
`prisma/seed.js` как реквизиты по умолчанию и в `services/email/templates.js`).

Версия кода в `package.json`: `6.0.0` (название пакета — `mibt`).

Это подтверждено кодом: Prisma-схема с моделями `Customer`/`Product`/`Order`/
`CustomerBalance`, ролевая модель `Role` (`ADMIN`/`CUSTOMER`), два типа клиента
`ClientType` (`CORPORATE`/`BUDGET`).

## Пользователи и роли (подтверждено кодом)

Ролей в системе всего две — `ADMIN` и `CUSTOMER` (enum `Role` в
`prisma/schema.prisma`), назначаются при логине в `req.session.role`
(`middleware/auth.js`: `requireAuth`/`requireAdmin`/`requireCustomer`).
Самостоятельной регистрации клиентов нет — учётные записи клиентов создаёт
только администратор (`POST /api/admin/customers`).

Два типа клиента (`ClientType`), определяющих модель оплаты:

| Тип | Значение | Модель оплаты |
|---|---|---|
| `CORPORATE` | B2B, корпоративный клиент | Баланс: пополнение → заморозка при заказе → списание при доставке |
| `BUDGET` | B2G, бюджетная организация | Баланс не используется — постоплата по факту (см. `services/order.service.js`) |

Источник для меток типов клиента в email: `services/email/templates.js`
(`clientTypeLabel`).

## Основной бизнес-флоу (подтверждено кодом и `docs/CHANGELOG_KEY_DELIVERY_REFACTOR.md`)

```
Клиент
  └─ Авторизуется (email + пароль)
  └─ Просматривает каталог (/catalog, /catalog/software, /catalog/hardware)
  └─ Формирует заказ (checkout получает актуальный баланс с сервера)
  └─ Заказ создаётся → для CORPORATE баланс замораживается на сумму заказа

Администратор
  └─ Видит новый заказ (статус PENDING)
  └─ Берёт в работу → IN_PROGRESS
  └─ Обрабатывает вручную: пишет комментарий клиенту (adminNote) и/или
     прикрепляет файлы (договор/счёт/акт/КП/спецификация/файл с ключами)
  └─ Может сгенерировать PDF-спецификацию автоматически (PDFKit) —
     сохраняется как OrderDocument типа SPECIFICATION
  └─ Завершает заказ → DELIVERED → для CORPORATE списание с баланса
     (для BUDGET — ничего не списывается, оплата вне системы)

Клиент
  └─ Видит статус заказа + комментарий администратора
  └─ Скачивает прикреплённые документы по одноразовой ссылке (TTL 5 минут,
     токен одноразовый — удаляется после использования)
  └─ Если заказ DELIVERED — видит расшифрованные лицензионные ключи,
     привязанные к строкам заказа вручную администратором
```

Отдельно — заявки на **коммерческое предложение (КП)**: клиент формирует
список товаров без оформления заказа (`QuoteRequest`), администратор
обрабатывает и прикрепляет документ КП, клиент скачивает его по такому же
принципу одноразового токена.

## Пополнение баланса (подтверждено кодом)

Клиент создаёт заявку на пополнение (`BalanceRequest`, статус `PENDING`) через
`/account/top-up`, администратор одобряет или отклоняет
(`PATCH /api/admin/balance-requests/:id/approve|reject`). При одобрении —
`creditBalance` с блокировкой строки `FOR UPDATE` и записью
`BalanceTransaction(CREDIT)`. Отклонить можно только заявку в статусе
`PENDING` (проверено кодом — соответствует исправлению, описанному в
`docs/TZ-balance-topup-fix.md`, Д-3).
